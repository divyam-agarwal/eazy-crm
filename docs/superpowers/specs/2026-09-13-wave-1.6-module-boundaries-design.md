# Part 2 — What the spike measured

A throwaway branch (`spike-modulith-verify`, deleted) added Modulith 2.1.1 test-scope, ran
`ApplicationModules.verify()` and `Documenter`, and was reverted. It replaces MA1–MA3 with
numbers. Raw notes: `scratchpad/modulith-spike-findings.md`.

## 2.1 MA2 — module detection: CONFIRMED

Exactly **seven** modules: `catalog`, `crm`, `demo`, `iam`, `platform`, `sales`, `tenant`.
`platform`'s 12 subpackages collapse into one module, as expected. `demo` is detected as a
first-class module, so MF4 is real.

## 2.2 MA3 — `Documenter` byte-stability: CONFIRMED, then found to be a false positive (Task 9)

16 files generated; **0 of 16 differ** between two consecutive runs into different folders. The
snapshot guard in M3/W9 is viable.

**Correction, Task 9:** this result was a false positive. Both generations ran inside the *same
test method in the same JVM* — exactly the context that hides the instability, because the
disorder is a function of execution context (how many other tests already ran in this JVM before
`ApplicationModules.of(...)` did), not of simply re-invoking the generator. Running the generator
twice from the same call site can never see that axis vary. Task 9 found the committed bytes
differ reproducibly between `./gradlew updateModulithDocs` (the sole test in its JVM) and
`clean check` (the same test running as roughly the 550th of 598, in a forked JVM) — same machine,
same JDK, same source commit. See challenge #79. The snapshot guard remains viable, but only
because `ModulithDocsSnapshotTest` now canonicalizes the unordered `Rel(...)` and `Component(...)`
runs before comparing bytes — not because `Documenter`'s output is byte-stable on its own.

## 2.3 MA1 — the violation count, and the finding that reshaped the slice

**446 violations, not the doc's floor of three:** 12 cycles + 434 "depends on non-exposed type",
0 of any other kind. The 434 concentrate in `platform.persistence.TenantScopedEntity`,
`platform.error.{NotFoundException,ConflictException,ValidationException}` and
`platform.web.PageResponse` — types every service legitimately shares.

**Then: declaring `platform` OPEN makes `verify()` pass with zero violations — all 12 cycles
included.** Every one of the 12 routes through `platform`, so opening `platform` removes them all
from the report.

**Isolated rather than inferred.** With `platform` still OPEN, a deliberately planted
`catalog → sales → catalog` cycle **is** caught (1 violation). So OPEN suppresses cycles *through
the open module*, not cycle detection in general.

**Consequence.** M2 ("take `verify()` as the build gate") and M4 ("declare `platform` OPEN") are in
conflict. The evaluation doc says OPEN "does not excuse the cycles, which must be fixed regardless"
— true, but it misses that OPEN removes the build's ability to *see* them. Adopt Modulith, declare
OPEN, fix nothing, and the result is a green gate certifying the graph that blocks SP8. Hence W4.
Logged as challenge #75.

## 2.4 API drift from the doc's 1.x-era assumptions

| Doc / tutorial form | Actual 2.1.1 form |
|---|---|
| `ApplicationModule.getName()` | `getIdentifier()` (or `getDisplayName()`) |
| `new Documenter(modules, "dir")` | `new Documenter(modules, Documenter.Options.defaults().withOutputFolder(dir))` |
| Modulith deps are test-only | `package-info.java` with `@ApplicationModule` needs `spring-modulith-api` at **compile** scope |

And one more version trap for the catalog's collection: **`repo1.maven.org`'s `maven-metadata.xml`
now reports `<release>2.2.0-M1</release>` — a milestone in the `release` field.** The evaluation
doc's rule "read repo1, not the search API" is necessary but not sufficient; the release field
itself cannot be read naively. **Latest stable is 2.1.1.**

# Part 3 — The design

## 3.1 Why `platform.visibility` is deleted rather than inverted

Inversion means declaring the interface in the *consumer* so the compile-time arrow runs opposite
to the call. It works only when what crosses the boundary names nothing of the provider's.
`AssignedWorkload` (challenge #66) succeeds because it returns `String` and `long`:

```java
public interface AssignedWorkload {          // declared in iam
    String label();
    long countOpenFor(UUID userId);          // primitives only
}
```

`VisibleFinder` cannot: its signatures are `Optional<Customer>`, `Page<Quotation>`,
`List<Quotation>`. The domain aggregates **are** the return values, so a port in `platform` still
imports `crm` and `sales`. `VisibilityPolicy` has the same problem in miniature — `viaCustomer()`
builds a criteria subquery with `Root<Customer>`.

A generic `Class`-keyed registry (`find(Customer.class, id)`) would preserve one chokepoint in
`platform`, at the cost of a generic API, an unchecked cast, and reshaping all 25 call sites. It was
rejected in favour of deletion, which is smaller and leaves `platform` with no visibility concern at
all for a future `master-data-svc` to inherit.

**Destinations:**

| Piece | Destination | Note |
|---|---|---|
| `unrestricted()` | **deleted as shared code** | `crm` and `sales` each derive it from the claim (§3.2) |
| `currentUserId()` | inlined at use sites | `TenantContext` is a public static utility read by ~22 classes across 11 packages; wrapping it is not a boundary |
| `SubjectType` | `sales` | W7 |
| `customers()` spec + all `CustomerRepository` reads | **`crm.CustomerVisibility`** | |
| the four `sales` specs, `viaCustomer`, `requireVisibleSubject` | **`sales.SalesVisibility`** | `sales → crm` already exists (`crm.Customer`, `crm.Contact`); `sales` already calls `findCustomer` in four places |
| `platform.visibility` (package) | **deleted** | MF1 closes by deletion |

**25 call sites across 11 files** change receiver, not shape: `finder.findCustomer(id)` becomes
`customerVisibility.find(id)`. Counted exactly: `findCustomer` 6, `requireVisibleSubject` 4,
`findQuotation` 4, `pageFollowUps` 2, `findEnquiry` 2, and one each of `pageQuotations`,
`pageOrders`, `pageEnquiries`, `pageCustomers`, `listQuotations`, `findOrder`, `findFollowUp`.

**Two further files reference `VisibleFinder` in javadoc only** — `sales/Activity.java` and
`sales/FollowUpRepository.java` — and must be updated with the rest. `platform/job/TenantJobRunner.java`
names `VisibilityPolicy` the same way (§3.3), as does `VisibilityScopingArchTest`'s comment. A
deleted class that survives in four comments is how the next reader learns the wrong architecture.

## 3.2 Restriction derived from the claim, per module

The role is already a JWT claim. `JwtService.mint` writes `.claim("role", role)`; `JwtService.parse`
reads `c.get("role", String.class)` into `TenantContext.TenantPrincipal(tenantId, userId, role)`.
**Nothing consults `iam` to obtain a role** — `iam.Role` is referenced in three `iam` files and
nowhere else. A dependency on `iam` would buy a *type*, not a capability, and would put a compile
edge from `sales` onto what becomes a separate deployable, undercutting decision I5 ("minting is
never delegated — only verification").

The precedent is already in the tree. `platform.security.RoleGuard` faced this and chose a string
literal, with its reasoning in the javadoc: *"It therefore compares the literal `"OWNER"` rather
than `Role.OWNER.name()` — `Role` lives in `iam`, and `TenantPrincipal.role` is a String
regardless."*

So each interpreter carries its own predicate:

```java
// crm.CustomerVisibility — and the same shape in sales.SalesVisibility
private static final String RESTRICTED_ROLE = "SALES_EXEC";

private boolean restricted() {
    return TenantContext.get().map(p -> RESTRICTED_ROLE.equals(p.role())).orElse(false);
}
```

`.orElse(false)` preserves today's deliberate **fail-open** for an absent principal — safe only
because this is a product rule and not the tenant wall; RLS still applies to every query built from
it. A String comparison is fail-open by construction; typing this on an enum would have made
`Role.valueOf()` throw on an unrecognised value, converting fail-open into a crash.

**The cost, stated plainly.** `"SALES_EXEC"` and the logic now exist in two places, and **H6's
`SALES_MANAGER` middle tier will have to be implemented twice**, where missing one fails *open* —
the direction that does not announce itself. This cost is not avoidable, only deferrable: post-split
the two services cannot share the method. Paying it now means H6 is designed for N independent
interpreters from the start. What replaces shared code is the discipline used across services —
a shared contract plus conformance tests (§4.2).

Recorded for later, out of scope here: `RoleGuard.requireOwner` is the same category — a shared
interpretation of a claim — and by this principle eventually migrates to per-module too.

## 3.3 `TenantJobRunner` (MF2)

It imports `tenant.{Tenant,TenantRepository,TenantStatus}` for exactly one purpose: enumerating
`TRIAL`/`ACTIVE` tenants. The port is therefore trivial, and only `UUID` crosses:

```java
// platform.job — declared by the consumer
public interface JobEligibleTenants {
    List<UUID> ids();
}
// tenant — supplies it; tenant -> platform already exists (4 imports)
```

Nothing about execution changes: `runAs` still wraps `tx.execute`, the template stays
`PROPAGATION_REQUIRES_NEW`, failure isolation is untouched. **Its javadoc names `VisibilityPolicy`
and must be updated** when that class is deleted.

## 3.4 The two ArchUnit rules

**Rule A — `platform` depends on no domain package.** No class in `com.easycrm.platform..` may
depend on `crm`, `sales`, `catalog`, `tenant` or `iam`. Zero violations once §3.1 and §3.3 land.
**This is the H4 gate**, because Rule A is not suppressed by `platform` being OPEN (W4). It is also
the slice's deliberately-failing first test (§4.1).

**Rule B — no cross-domain repository access.** No domain package may depend on another domain
package's `*Repository`. Four violations exist today, each allowlisted with a named exit — the
idiom of `TenantScopingArchTest.GLOBAL_TABLES` and `VisibilityScopingArchTest.ALLOWED_METHODS`,
where an entry is a decision that costs review:

| Edge | Site | Reads | Exit |
|---|---|---|---|
| `sales → crm.ContactRepository` | `ShareLinkService:129` | `findByCustomerId` — the `wa.me` recipient | **Synchronous internal call.** Already designed: `GET /internal/customers/{id}/contacts/primary`, master-data → document, in the service-scope doc §1.2. A routing address needs freshness, which is why S2's freeze was declined |
| `sales → catalog.ProductRepository` | `PriceResolver:46` | `findById` | **Synchronous internal call, fail-fast 503.** Service-scope doc §1.3: "Price list item, product → master-data. Fail fast, 503" |
| `sales → catalog.PriceListItemRepository` | `PriceResolver` | price lookup | Same |
| `sales → tenant.TenantRepository` ×3 | `ShareLinkService:98`, `QuotationService:328`, `QuotationPdfService:92` | `findById` — the seller's own profile | **Freeze, not a call.** The letterhead belongs in `document-svc`'s immutable render payload (service-scope §1.4, F13). See H7 (§5.3) — today it is a live read and that is a defect |
| `iam → tenant.TenantRepository` ×3 | `AuthService`, `MemberService`, `InvitationService` | `findBySlug`, `findForUpdate`, `findById` | **None needed — intra-service.** `identity-svc` owns both `iam` and `tenant` (service-scope §1.1), so this edge does not cross a service line |

The last row is why Rule B allowlists rather than forbids: not every cross-package repository read
is a future cross-service read, and the rule's value is in making the distinction explicit.

## 3.5 Modulith adoption

BOM 2.1.1; `spring-modulith-core` and `-docs` at test scope, `spring-modulith-api` at compile scope
(§2.4); `platform` declared OPEN via `package-info.java`; a `ModularityTest` calling `verify()`;
`Documenter` output committed and snapshot-guarded (W9); ArchUnit pinned to 1.4.2 (W10).

**With a non-vacuity assertion, because of what §2.3 found.** The test pins that seven modules and
a non-trivial class count were actually imported, so the gate cannot pass by reading nothing — the
same discipline as `PlatformPrimitivesArchTest.theImportIsNotVacuous`, and the same failure family
as the ArchUnit 1.3.0 note in the catalog and challenge #72's vacuous CI check. The `ModularityTest`
must also carry a comment stating that it does **not** cover `platform` cycles and naming Rule A as
what does.

# Part 4 — Test strategy

## 4.1 The deliberately-failing first test

**Rule A, written first**, failing on the 18 imports in `VisibleFinder` (10), `VisibilityPolicy` (5)
and `TenantJobRunner` (3). Then the fix makes it pass. Structural rather than behavioural, which
suits a refactor that changes no behaviour — and the same opening move as `a3d89f1` in the
buyer-snapshot slice.

## 4.2 New tests

- **Role → restriction conformance**, which both `crm.CustomerVisibility` and
  `sales.SalesVisibility` must pass: `OWNER`, `SALES_MANAGER`, `SALES_EXEC`, an unrecognised role,
  and no principal. This is what replaces the shared method (W3), so it is the slice's most
  load-bearing new test.
- **Literal/enum agreement**, test scope only: the role literals used in `crm`/`sales`/`platform`
  match `iam.Role`'s constants. Tests may depend on anything, so this recovers compile-ish safety
  without a production edge.
- **Rule A**, **Rule B** (with its allowlist), and the **Modulith non-vacuity** assertion.

## 4.3 Must stay green, untouched — the behaviour-neutrality proof

`crm/CustomerVisibilityTest`, `sales/EnquiryVisibilityTest`, `sales/FollowUpVisibilityTest`,
`sales/QuotationOrderVisibilityTest`, `sales/ActivityVisibilityTest`, `sales/NestedVisibilityTest`,
`TenantScopingArchTest`, `RlsCoverageIntegrationTest`, `ActivityRepositoryScopingArchTest`,
`PlatformPrimitivesArchTest`, and `OpenApiSnapshotTest` — **no API surface moves in this slice.**

`platform/visibility/{VisibleFinderIntegrationTest,VisibilityPolicyIntegrationTest,RequireVisibleSubjectTest}`
move with their subject to `crm` and `sales`.

## 4.4 Restated deliberately

`VisibilityScopingArchTest` (W6). The spec's §8 rule it implements — "the ONLY class permitted to
call a read method on the four visibility-scoped repositories" — becomes per-repository. **The
restatement must be justified in the test's own javadoc**, or it will read as a weakening to the
next person.

# Part 5 — What this slice does not do

## 5.1 The three layers of split-readiness

| Layer | What it is | State |
|---|---|---|
| **1 — package acyclicity** | `platform` is one shared library every service takes, so it must depend on no domain package | **This slice.** H4, Rule A |
| **2 — cross-service data access** | Direct reads of another service's tables, and joins across them | **Frozen, not fixed.** Rule B's register; design owed (§5.2) |
| **3 — schema** | FK constraints across future service lines | **Already clean.** Zero `REFERENCES` in all 34 migrations; `quotation.customer_id` is a bare indexed `UUID`. Nothing to drop at extraction |

Layer 1 is necessary and nowhere near sufficient. Neither Modulith nor Rule A can see Layer 2,
because a cross-service read is not a cycle.

## 5.2 Layer 2 needs its own design, and does not have one

Rule B's allowlist is a register, **not a permanent exemption** — each entry is to be removed via a
synchronous internal call, an event, or a freeze, per §3.4's exit column. The roadmap has no design
for this: SP8 is listed as conditional/XL, and the service-scope doc that names the edges is known
to be stale (its own §3.2 records that its findings predate the files that broke them). A
cross-service data access design is added as its own roadmap item, ahead of SP8.

`viaCustomer` is the sharpest case. Moving it into `sales` (§3.1) fixes the package cycle but leaves
a **cross-service SQL join** — `sales` rows filtered against `crm`'s `customer.assigned_to` — that
now *looks* local. The split-ready answer is for `quotation`/`sales_order` to carry their own owner,
synced from the customer, so `sales` filters without touching `crm`'s table. That is a data-model
change with an event behind it and belongs to the Layer 2 design. **This slice must record the move
as not-yet-split-ready rather than let the relocation imply otherwise.**

## 5.3 H7 — the seller is not frozen, and the tax presentation depends on it

Found by this slice's audit of what `sales` reads from `tenant`. In `QuotationPdfService.render`,
two lines apart:

```java
BuyerSnapshot buyer = v.getBuyer();                      // frozen at send()
Tenant tenant = tenants.findById(TenantContext.tenantId())  // read LIVE
...
boolean interState = !v.getPlaceOfSupply().equals(tenant.getStateCode());
```

The buyer block is frozen; the seller block — `businessName`, `gstin`, `address`, `phone`, `email` —
is live. **And line 99 computes the tax presentation from the frozen `placeOfSupply` against the
live seller `stateCode`**, so a tenant changing their registered state flips an already-`SENT`
quotation between CGST/SGST and IGST rows on re-render, through the public share link the buyer
already holds. `send()` rejects with 422 when the *customer's* `stateCode` diverges from the frozen
`placeOfSupply`; nothing guards the seller's.

This is H1's exact class, on the other side of the document. The buyer-snapshot spec does not
mention the seller, letterhead, or tenant profile anywhere. It needs its own freeze decision — which
seller fields freeze, and at `send()` or at version creation, by challenge #69's test ("was anything
already frozen *derived* from this field?", and for `stateCode` the answer is yes) — so it is
recorded as **H7** and not folded in here.
